# 宠物养成小程序阶段性开发文档

更新时间：2026-04-28

## 1. 文档目标

这份文档不再只做“产品设想罗列”，而是用于指导当前项目迭代，解决三个问题：

- 哪些功能是当前版本必须先做完的
- 哪些功能适合放到下一阶段，而不是过早展开
- 当前前端和后端已经做到了哪里，还缺什么

当前判断：原始分析方向是对的，但第一阶段内容偏多，且部分描述与现在的技术路线不完全一致。项目应按“基础可用 -> 数据闭环 -> 增值能力 -> 生态延展”推进。

## 2. 当前产品主线

围绕“记录一只或多只宠物的日常生活，并逐步沉淀成长期档案与服务入口”展开，核心主线保持不变：

1. 宠物档案管理
2. 日程提醒
3. 花销与护理记录
4. 时间线 / 报告
5. 食物与用药管理
6. 知识库 / 问答
7. 用户页与反馈入口

不建议当前阶段把重心放在：

- 过早做商城闭环
- 过早做社交广场
- 过早做硬件联动
- 过早做复杂会员权益拆分

这些方向可以保留，但不应抢占当前核心开发资源。

## 3. 需求修正版

### 3.1 需要修正的几点

原始分析中以下内容建议调整：

- “本地存储不丢失”需要改为“云端存储为主，本地缓存为辅”。
- “MVP 1-2 个月内覆盖相册、知识库、打卡、通知、勋章”等内容偏重，建议缩减。
- “最多 3 只宠物”“最多 50 张照片”这类限制，不适合先写死为核心需求，更适合做产品策略配置。
- “AI 问答、会员、商城、社交、地图、硬件”属于后续增强项，不应与基础记录闭环放在同一优先级。

### 3.2 当前更合适的阶段划分

建议改为四层：

- V1：基础可用版
- V2：数据闭环版
- V3：增值能力版
- V4：生态扩展版

## 4. V1 基础可用版

### 4.1 阶段目标

先完成最核心的“养宠记录闭环”，让用户能顺畅完成：

`登录 -> 建档 -> 添加提醒 -> 添加记录 -> 查看统计/时间线 -> 查知识`

### 4.2 V1 必做功能

#### A. 账号与基础框架

- 微信登录
- 当前用户信息获取
- 宠物维度的数据隔离
- 统一页面导航与主链路跳转

#### B. 宠物档案

- 添加 / 编辑 / 删除宠物
- 基础字段：姓名、类型、品种、生日、性别、体重、颜色、绝育状态、备注
- 宠物列表与宠物切换
- 单只宠物详情页

#### C. 日程提醒

- 提醒新增 / 编辑 / 删除
- 提醒分类
- 提醒时间
- 重复规则
- 已完成 / 待处理状态
- 日历和列表查看

#### D. 基础记录

- 花销记录
- 护理记录
- 日常记录
- 所有记录都必须关联宠物

#### E. 食物 / 用药 / 里程碑

- 食物记录
- 用药记录
- 成长里程碑记录

这三个模块在 V1 可以先完成“可增删改查 + 列表展示”，不需要一开始就做复杂算法。

#### F. 基础聚合展示

- 宠物概览
- 宠物时间线
- 我的页聚合数据
- 档案页聚合数据
- 基础报告页

#### G. 知识库

- 分类浏览
- 文章列表
- 文章详情
- 关键词搜索

#### H. 反馈入口

- 反馈提交
- 联系方式提交
- 反馈列表查看

### 4.3 V1 暂缓项

以下内容不建议放入第一阶段硬性验收：

- 勋章体系
- 打卡挑战
- 主题换肤
- Excel 导出
- 微信服务通知
- AI 问答个性化推荐
- 社交分享
- 商城功能

### 4.4 V1 验收标准

- 主链路可完整跑通
- 每个核心模块都能完成新增、查看、更新、删除或软删除
- 页面可演示，空态、无宠物态、未登录态清晰
- 前后端数据模型基本稳定

## 5. V2 数据闭环版

### 5.1 阶段目标

在 V1 可用的基础上，把“记录系统”做成真正有复用价值的数据产品。

### 5.2 V2 核心能力

- 花销按时间 / 分类 / 宠物维度统计
- 护理记录与日程联动
- 时间线体验完善
- 报告页指标更完整
- 食物库存预警
- 用药剩余天数 / 临期提醒
- 知识库收藏
- 问答历史
- 管理后台基础能力或管理页能力

### 5.3 V2 可加入的轻运营能力

- 基础打卡模板
- 基础勋章展示
- 基础主题皮肤

这些内容可以做，但优先级应低于“数据准确、模块稳定、查询性能”。

## 6. V3 增值能力版

### 6.1 阶段目标

在数据闭环稳定之后，再引入能提升留存和付费价值的能力。

### 6.2 V3 适合引入的功能

- AI 问答
- 智能提醒推荐
- 饮食推荐
- 健康异常预警
- 年度成长报告优化
- 更完整的会员体系
- 更强的分享能力

### 6.3 V3 前提条件

要进入这一阶段，前置条件至少包括：

- 记录字段相对稳定
- 聚合统计接口稳定
- 用户行为链路已有基本留存
- 后端权限和查询性能已经收口

## 7. V4 生态扩展版

这一阶段保留为中长期规划，不作为当前开发排期承诺：

- 商城闭环
- 区域伙伴地图
- 周边医院 / 宠物店 / 寄养服务
- 轻社交动态
- 应急求助
- 硬件联动

这些方向都合理，但需要在基础产品跑稳后再做。

## 8. 当前项目与需求对照

以下判断基于当前前端页面、已接入接口以及现有代码结构。

### 8.1 已有较完整基础

- 登录：已有 `Login` 页面和认证接口
- 宠物档案：已有宠物列表、编辑、详情、概览
- 日程提醒：已有日程页、提醒新增、提醒列表
- 基础记录：已有花销、护理、日常记录链路
- 食物 / 用药 / 里程碑：已有独立页面和接口
- 时间线 / 报告 / 服务页：已有页面和聚合接口
- 知识库：已有分类、列表、详情、收藏、问答、问答历史
- 反馈：已有反馈页和反馈接口

### 8.2 已有但仍需补质量

- 页面文案质量和部分乱码问题
- 多页面视觉规范不统一
- 二级页面完成度不一致
- 演示态与真实接口态混用
- 聚合页的数据准确性与接口边界仍需继续核对

### 8.3 当前明确还不该急着做

- 商城
- 复杂会员权益体系
- 社交广场
- 区域服务地图
- 智能硬件

## 9. 当前版本建议排期

### 9.1 第一轮

目标：把 V1 做扎实。

优先顺序：

1. 修正文案与乱码
2. 统一主链路页面体验
3. 补齐各模块空态 / 异常态 / 无宠物态
4. 核对前后端字段与接口返回
5. 修正后端聚合查询和权限边界

### 9.2 第二轮

目标：把 V2 的核心数据闭环做好。

优先顺序：

1. 花销统计优化
2. 护理 / 提醒联动
3. 食物库存和用药提醒
4. 时间线与报告页指标补齐
5. 知识库收藏与问答体验优化

### 9.3 第三轮

目标：再决定是否进入智能化和会员能力。

只有当基础记录产品稳定后，再考虑：

- AI 问答
- 智能提醒
- 健康预警
- 会员权益

## 10. 前后端协作建议

### 10.1 前端重点

- 优先统一主链路页面体验
- 让各页面都围绕真实接口工作
- 把“展示页”逐步过渡成“业务页”

### 10.2 后端重点

- 收口认证方式
- 清理聚合查询的重复和性能问题
- 保证所有数据严格按用户和宠物隔离
- 统一 DTO 校验和返回结构

### 10.3 联调重点

- 时间字段统一格式
- 分类字段统一枚举或约定值
- 软删除后列表刷新逻辑统一
- 聚合页字段命名固定下来，避免前端频繁适配

## 11. 最终结论

原始文档的方向没有问题，核心模块判断也是对的，但如果直接按原稿推进，第一阶段会过重，容易一边做基础能力一边被营销、会员、商城、AI 分散精力。

更适合当前项目的做法是：

- 先把 V1 基础可用版做扎实
- 再把 V2 数据闭环和统计能力做好
- 最后再决定哪些增值能力值得继续投入

当前项目实际上已经具备了较好的 V1 骨架，接下来最有价值的事情不是继续扩概念，而是把已有模块做稳、做顺、做统一。
